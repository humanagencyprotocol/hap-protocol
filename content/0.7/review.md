This document is the **forward ledger**: what is open, what it targets, where the specification currently leads its reference implementation, and which deviations and audits are on record. What was promoted into v0.7 and why — the vocabulary release, its renames, retirements, and the proposals considered and rejected — is `changelog.md`. A v0.7 implementation MAY implement any direction below without losing conformance, and MAY skip all of them without losing conformance.

Each open direction carries an explicit **target**; "undated" means no version commitment exists yet.

---

## The v0.7 migration itself — implementation status

v0.7 renames signed fields, profile fields, error codes, and a required gate (`protocol.md` → *Migration from v0.6*). At the time of writing (checked against the code on 2026-08-31 and again on 2026-09-03) the reference implementation is a **v0.5 wire with v0.6 features**: the AS issues `version: "0.5"` mandates that still carry `resolved_domains` — a field the v0.6 specification dropped — alongside `resolved_owners`; the core library's version type stops at `'0.6'`; error codes are not canonical (register 2 below); `contextSchema` and `decision_owner` are read everywhere. Content binding, read authorization, identity assurance, and the custody archive are real; the version stamp is not. The vocabulary gap is register 1 by construction — nothing is wrong for any existing artifact until the implementation claims v0.7 — but the version stamp and the error codes are register 2, because the v0.5 and v0.6 specifications already required them. The order is fixed by dependency: core library types and conformance vectors → Authority Server (issue `0.7`, verify `0.6`) → Gatekeeper (custody archive is already in place; `mandate_owner` gate; new error codes) → a new version of every profile (`scopeSchema`, `ownerSignature`, `ticket_lookup`, `appliesTo`) → conformance suite → public and product copy. The implementation plan lives with the implementation (`doc/v07-plan.md`), not here.

## Owner Signatures — implementation phasing (specification-led since v0.6)

The normative design is in `protocol.md` → *Owner Signatures*; it was promoted specification-led in v0.6 (rule 3). Status per phase:

| | | Size | Status |
|---|---|---|---|
| **P1** | Types: owner-signature entries, mandate projection, approval objects, `approvalSignature` ticket field, error codes, deprecation of `Subject.owner_signature`; a `did:key` encoder/decoder in the core library | small | **done 2026-08-13** (core library 0.9.0) — **to be redone under the v0.7 names**: `mandate_owners` merges the two v0.6 lists, the projection `typ` changes, and the codes are renamed |
| **P2** | WebAuthn registration and real key-bearing signing DIDs in the AS; signing in the locally installed gateway UI; `verifyMandate` in the core library; owner signatures in the public ticket projection | large — the real work | open |
| **P3** | Approval signatures end-to-end; ticket-route enforcement; `approvalSignature` in the ticket | medium | open |
| **P4** | Verifier policy surface: minimum-`binding` configuration, DID pinning, out-of-band acquisition UX | small–medium | open |
| **P5** | `binding: "eudi"` — and with it, key rotation | configuration, not redesign | open |

P5 being configuration rather than redesign is the point of the ordering: build the slot against key material that exists today (passkeys), and a national scheme plugs into it. **Dependency worth naming:** the reference AS has no WebAuthn today. P2 is new ground, not a patch.

## Deviation notes

### D1 — Profile in-place mutations (grandfathered, closed)

The immutability rule was violated four times by the reference implementation: `content_binding` was added **in place** to the published `records@0.4` / `customers@0.4` (June 2026) and then to `email@0.4` / `publish@0.4` (July 2026). No version bump, no re-issuance. Tolerable in practice — the authority contract the human signed was untouched, tickets are self-contained, and the fields were OPTIONAL — but wrong: an annotation that changes what future tickets publicly expose is a behavior change, and for `email` it changed the privacy posture of already-signed mandates without their being re-signed. v0.6 closed the loophole normatively (no annotation exemption). These four mutations are grandfathered; implementations MUST treat them as the last of their kind.

### D2 — Decorative `did:key` identifiers (open, migration required)

The reference AS mints owner DIDs as `did:key:` followed by a truncated random UUID — an identifier wearing `did:key`'s clothes with no key in it and no self-certifying property. Under `protocol.md`'s conformance rule such a DID MUST NOT sign, and its failure is structural (there is no key to verify against — deliberately, since the wire format carries no `public_key`). Existing identifiers MAY remain for audit continuity and as identity DIDs; **new signing DIDs MUST be real key-bearing DIDs**. The related finding — the reference AS signed a **caller-supplied** owner DID without checking it against the authenticated identity — is forbidden by *Identity & Authorization* rule 6. Both are P2 work.

### D3 — The field-name fallback for cumulative bounds (open, closes on a condition)

Both reference enforcement points still carry a fallback that selects a cumulative bound by field-name correlation when a profile declares no `appliesTo` — the mechanism `protocol.md` → *Bounds Schema* rule 3 forbids. As of 2026-08-27 every published profile declares `appliesTo`, so the fallback is no longer load-bearing for them; it remains reachable for mandates on older profile versions. It MUST be deleted, and **not before every live, unexpired mandate sits on a profile version that declares `appliesTo`** — a mandate on an older version would otherwise fall through to "every count bound applies", and a small `delete_daily_max` would begin refusing writes. Mandate TTLs bound the wait; the condition to check is that no live mandate references a pre-declaration version. Until then the deviation stands, deliberately, rather than half-closed.

## Status notes — where the v0.7 spec leads its reference implementation

Two registers, deliberately kept apart.

**Register 1 — specification-led by design (harmless while absent).** Additive and optional; absence changes nothing for existing artifacts, and no conformance claim is violated by not having them:

- **The v0.7 vocabulary on the wire** — see the section above; nothing claims v0.7 yet.
- **Owner signatures P2–P5** — phasing above.
- **Conformance vectors — published; consumption open.** The four sets exist as normative data at `content/0.7/vectors/` (canonical bounds and scope hashes including the absent-optional-key rule, the `charge@0.5` profile hash, six payload signatures under the RFC 8032 §7.1 published test keys — including a co-signed mandate that chains to the standalone projection so the two-signature composition is pinned, not only each signature separately — and the required-refusal tables), each value computed and then re-derived by an independently written implementation before publication. What remains is the other half: **no implementation reads them yet.** Before v0.7, the v0.5 deliverable and Invariant 9's "MUST publish at least one signing test vector" were unmet in a way worth recording — the vectors existed only in the core library's test file (`test/mandate-vectors.test.ts`), which the published package does not include (`files: dist, src`), so no third party could obtain them. Closes when the core library's tests consume the published files instead of carrying their own copies (the canonical-bounds set is consumed as of the `fix/canon-escaping-and-fail-closed` branch; the payload set waits on the v0.7 types), and the conformance suite drives the refusal tables.
- **Five additive signed fields** (`issuer`, `profile_hash`, ticket `version` and `mandateId`, `disclose_fields`), the conditional projection fields, co-signed `expires_at`, *Version negotiation*, and the signing-key rotation rule — specified in v0.7, not built.
- **Ticket disclosure declarations** (`disclose_fields`) — the default-none principle is normative; no profile declares any disclosure yet and no implementation reads a mandate-level declaration. Silence *is* the specified behavior.
- **A wire binding.** The specification defines artifacts, behaviours, and refusals, and deliberately no endpoints, request authentication, response envelope beyond the `{approved, errors}` shape, proposal object, or approval transport. Two implementations built from the text alone verify each other's artifacts and cannot talk to each other. Not a conformance gap — a stated limit of interoperability. Direction: a non-normative companion `hap-http-binding@0.1` (paths, methods, auth header, envelope, proposal and approval transport, revoke, verify, `.well-known` key discovery) that the reference implementation adopts, so a second implementation can be tested against it; and JSON Schemas for the six artifact types, the profile, and the manifest, published beside the vectors. Undated.

**Register 2 — normative MUSTs not yet met: the reference implementation is currently non-conformant on these points.** Stated in those words because it is the uncomfortable, accurate status:

- **Per-correspondent overrides** (*Read Authorization*) — specified, not built (helpers reserved, unused).
- **Displayed-must-be-bound** — no enforcement exists, and there is a live, known case: an approval surface displays `bcc` while the binding deliberately omits it. Defensible only because review-mode proposal matching independently pins the whole argument set — which is exactly the "second mechanism MUST be stated" clause; that statement still needs to move from this ledger into the relevant profile/manifest metadata.
- **`appliesTo` fallback** — D3 above: conformant for every live profile, non-conformant in what the code still allows.
- **Canonical error codes are not emitted.** The specification says "implementations MUST emit exactly these codes." The reference AS's ticket route returns `LIMIT_EXCEEDED` — retired in v0.5 — for every bound kind; neither `BOUND_EXCEEDED` nor `CUMULATIVE_LIMIT_EXCEEDED` is emitted anywhere in the AS. The core library emits `BOUNDS_MISMATCH`, `CONTEXT_MISMATCH`, `FRAME_MISMATCH`, `DOMAIN_NOT_COVERED`, `INVALID_PROFILE`; the AS adds `NOT_AUTHORIZED_FOR_ATTESTATION`, `MISSING_FIELDS`, `ATTESTATION_NO_GROUP`, `PROFILE_BOUND_UNCONFIGURED`, `COMMITMENT_MODE_UNREADABLE`, `PROFILE_NO_BOUNDS_SCHEMA` and others outside the canonical set. The reference AS would fail conformance vector set 3 — its own refusal table — as it stands. This predates v0.7 and is the first implementation item in `doc/v07-plan.md`, because the refusal vectors cannot be written until the two agree.
- **Version stamp.** The AS issues `version: "0.5"` with `resolved_domains`; the v0.6 specification required `"0.6"` without it.
- **Authority Server, found 2026-09-03 (second advisor review; fixes on branch `fix/as-security-2026-09`, not yet released):** an `x-github-token` header minted an authenticated owner identity from the token's first eight characters with no validation (`src/lib/auth.ts`) — an unauthenticated identity path; a mandate request could carry `bounds_hash` without plaintext `bounds`, after which the AS enforced no bounds at all at ticket time (`attest/route.ts`, `receipt/route.ts`); group mode checked membership but never required-approver status, so any active member could obtain a mandate; the signed mandate blob was TTL-evicted from storage at `expires_at`, so the artifact an auditor needs did not survive the mandate (`authz-store.ts`). Two consequences of the fixes an operator must plan for before release: a team group whose profile has no configured approvers can no longer obtain mandates at all (the spec's rule; a data audit of group profile configs must precede deploy, and the "caps with no approvers" hard-ceiling mode no longer exists as a grantable configuration), and mandate blobs are now retained without expiry until an explicit retention sweep exists (delete only after expiry plus `retention_minimum`). Still open on the AS: `boundsHash` is not the ticket lookup key (the `authz_<uuid>` is required and the hash is an optional cross-check — the inversion of ticket rule 1) and the ticket carries `authorizationId` and `path` instead; signatures are standard base64, not base64url; the redacted public ticket page shows "Signature: Valid ✓"; group limit ceilings read a keyspace nothing writes; the field-name fallback can *skip* a configured count bound; profiles are fetched from a mutable branch at runtime with no retained bytes; no issuer DID, no key rotation; `review_above_cap` is rejected as a mode.
- **Gateway, found 2026-09-03 (fixes on branch `fix/gateway-privacy-and-gating`, not yet released):** the content-hash preimage (`boundContent` — for email the recipients, subject and body) was spread into every ticket request and sent to the AS, contradicting the Privacy Invariant and the code's own comment; cumulative bounds were enforced from the local 31-day execution log before the AS was consulted, which *Executor Gating* forbids; a tool absent from a manifest fell through to the manifest's `default` gating instead of being refused. Still open on the gateway: no signed above-cap approver list exists, so AS-supplied approvers are used verbatim; the AS public key is fetched from the AS and cached with no pin; `scope_hash` is verified only when scope is non-empty; the review path re-issues a ticket without re-running Phase 1; post-fetch age enforcement is omitted for list/search tools; error handling is HTTP-status and regex based (revocation detected by `/revoked/i` on message text).
- **Core library, found 2026-09-03 (fixes on branch `fix/canon-escaping-and-fail-closed`, not yet published):** `verify()` returned `approved: true` for an empty mandate list — no signature, TTL, or hash verified — when no bound was violated; value escaping (above) is being implemented; `scope_hash` is checked only when scope is non-empty; `commitment_mode` and owner coverage are never read by `verify()`.
- **Profiles, found 2026-09-03:** `customers@0.7` and `email@0.6` carry `paths` arrays on bounds fields (Bounds Schema rule 6 forbids reintroduction); `deploy@0.9` carries a deprecated `field.enum`; `email@0.6`'s `read_daily_max` declares `appliesTo: []`; the only profile lint (`hap-e2e/test/profile-conformance.test.ts`) checks three rules and passes all of these. Each needs a new profile version — no in-place edits (D1).
- **Conformance map:** `hap-e2e/conformance/core-musts.ts` marked `GK-local-log-display-only` and `GK-every-tool-in-manifest` as held by tests that did not test them; corrected on branch `fix/conformance-map`.
- **Absent optional bounds keys rendered as the literal text `undefined`** (found 2026-09-03 while fixing value escaping on `hap-core` branch `fix/canon-escaping-and-fail-closed`). The canonical form for a key the human did not set was never specified; the reference library emitted `key=undefined`, and two independent copies of the canonicalizer — the gateway's browser-side `apps/ui/src/lib/frame.ts`, which mints the hash the human signs, and `hap-e2e/src/helpers/crypto.ts` — do the same. v0.7 now specifies omission (*Canonicalization Rules*; vectors `bounds-optional-key-absent`, `scope-empty-string-value`). **Migration consequence:** every live mandate whose bounds omit an optional key (the `email@0.6` templates omit two) changes hash under the corrected rule; the AS re-binds stored bounds to the signed hash at ticket time, so such mandates fail **closed** (`BOUNDS_HASH_MISMATCH`) the moment a corrected library is deployed on either side, and must be re-issued. All three canonicalizers MUST move in one release train — a UI on the old rule signing for an AS on the new one is exactly the disagreement the vectors exist to catch. Fully-populated bounds (charge, records, purchase) are unaffected.
- **Value escaping in bounds and scope canonicalization is not implemented** (found 2026-09-03 while building the conformance vectors). *Canonicalization Rules* has required since v0.5 that a value containing `=`, `%`, or a byte outside printable ASCII be percent-encoded, and that a value containing a raw newline be **refused** rather than normalized. The core library's `canonicalBounds` / `canonicalContext` interpolate values with `String(v)` and apply neither rule: a bound or scope value with an `=` in it produces a hash no conformant implementation reproduces, and a value with an embedded newline produces a canonical string whose line structure no longer matches its own key order — silently, since the hash is still well-formed. No live profile is known to carry such a value, which is why this survived unnoticed; that is luck, not enforcement. The published vectors pin both rules (`canonical-bounds-and-scope.json`, cases `scope-percent-encoding` and the two `must_refuse` entries), so the gap now fails a check instead of waiting for a second implementation to find it.

**Conformant, recorded so the spec is not read as a description of the implementation:**

- **Gatekeeper custody** (promoted in v0.7) — the reference gateway has kept an append-only, locally encrypted, unpruned ticket archive, deduplicated by ticket id and distinct from the 31-day cumulative-display log, since August 2026. Two gaps against the v0.7 text: the issuer public key per entry is **optional** in the archive (`asPublicKey?`) where the specification requires it, and the archive is **best-effort by contract** ("callers MUST NOT let an archive failure block an execution") where the specification now says an unarchivable ticket MUST NOT be executed. Both are small; the second is a deliberate reversal of the implementation's choice, decided in the 0.7 advisor round.
- **Revocation is permanent** (promoted in v0.7) — the reference AS has enforced it with per-ceremony mandate identity since July 2026.
- **`actionTypes` and `appliesTo`** — declared by all eight published profiles as of 2026-08-27 (`calendar@0.5`, `records@0.5`, `publish@0.5`, `purchase@0.5`, `charge@0.5`, `email@0.6`, `customers@0.7`, `deploy@0.9`); the AS refuses a ticket request with no `actionType` and validates registry membership; the Gatekeeper fails closed on a write whose manifest declares none; a cross-repo test holds the latest version of every profile to both declarations. One registry entry is worth keeping on the record: `charge@0.5` lists `unclassified` alongside `charge` and `subscribe` — see *Read classification for remote connectors* below.

**Declaration-class, recorded so its status is not forgotten:** `signing_surface` is normative and explicitly a **declaration, not a proof** — it carries information no verifier can check, honest only because there is no incentive to overclaim protection to the party weighing it. If a checkable variant ever exists (an attested-surface mechanism), it would be a new field, not a reinterpretation of this one. The same holds for the deployment *declared posture* in `governance.md`.

## Open directions

### Retire the field-name fallback — targets the first release after the D3 condition holds

Step 1 (specify `appliesTo`) landed in v0.7. Step 2 is deletion of the fallback in both reference enforcement points, gated on the D3 condition. Recorded here as well as in the deviation so the closing release has something to point at. Procedural lesson carried forward from v0.6: a fix that changes what a *profile* may declare is a protocol change wearing a bug fix's clothes, and it belongs in the ledger the day it ships.

### Sub-mandates and hierarchies of accountability — undated

The protocol's building blocks — groups, required approvers per profile, `review_above_cap` with named approvers, multi-owner mandates — already support **hierarchies of accountability** in place of hierarchies of supervision. What flows down is authority, not instructions; what flows up is exceptions and tickets, not reports. Span widens (a mandate holder can hold dozens of sub-mandates if most activity runs automatically), depth collapses (a layer exists only where a distinct scope of accountability exists), and failure handling becomes surgical (revoke one branch). The organizing rule: **each mandate may only grant less than it holds.**

What is not yet a protocol object: a sub-mandate cannot cryptographically prove that it nests inside its parent — that its bounds are a subset, its scope narrower, its expiry no later, its commitment mode no looser. Today that relation is organizational configuration on the AS, an honest-operator control. Making it compromise-resistant evidence means a signed reference from child to parent plus a verifiable subset relation over bounds and scope — the second of which needs the per-field commitments below to be checkable without disclosing the parent. Between independent operators the same mechanism forms a **mesh** — temporary trees per undertaking on a permanent network of sovereign nodes, with a locally operated Authority Server as civic infrastructure. Cross-server federation remains deferred (`governance.md` → *Multi-AS Ecosystem*); a discovery layer over ticket histories is out of scope and carries the privacy cost the specification already names under *Read Authorization*.

### Read classification for remote, vendor-controlled connectors — undated

`charge@0.5` names an action type called `unclassified`, and the reason generalises past Mollie. A connector reached through a remote MCP server the operator does not control has a tool list that cannot be enumerated when its manifest is written and can change without notice. The manifest therefore gates anything it does not explicitly classify as a **write** — fail-closed, and correct. The cost is precision: genuine reads on such a server are counted as consequential, consume a write budget, and produce tickets — over-restrictive rather than unsafe, but it means a ticket exists for something no one executed. Classifying those tools needs the live tool list, which needs credentials, so it is operational work. What the specification could add is a name for the situation: a declared *unclassified* action class, so a ticket carrying it reads as "this connector could not tell what this was, and treated it as consequential" rather than as a positive claim about the action.

### Dual-signed public ticket projection — targets v0.8 (slipped from v0.7; reason in `changelog.md`)

> **Security dependency, not only a transparency improvement.** Invariant 10 permits a ticket-demanding effector to satisfy Complete Mediation, and such an effector must establish the ticket's authenticity itself. Today it cannot: the public projection withholds the signature, so the effector asks the Authority Server whether the signature is valid and its mediation therefore depends on the AS being both honest and reachable — an honest-operator control where the invariant demands compromise-resistant evidence (`protocol.md` → *Enforcement classes*). The dual-signed projection is what closes that.

The public ticket view deliberately redacts private fields **and the signature**; because one Ed25519 signature covers the whole ticket, the public page cannot be independently re-verified — its "signature valid" is the AS re-verifying itself. Full zero-trust verification is available only to the holder of the complete signed ticket, which for a *private* action is the party that matters. For a *public* artifact "everyone is the holder," and the gap is real.

The fix: the AS separately signs a public-only projection `{id, timestamp, profileId, actionType, boundsHash, contentHash, contentBinding, identity, issuer}` and exposes it with its signature — carrying `boundsHash` (the mandate reference) and, where present, the owner's signature entry from `mandate_owners`, because without those the ticket → mandate → owner-signature chain cannot even start from the public view — extended by two requirements the deploy work surfaced when the ticket became a **bearer proof presented to a third party**:

1. **Replay.** Idempotency is retry-dedup, not replay defence. A ticket presented twice to an external verifier is a different problem; content binding contains most of it, but an old ticket could force old, vulnerable code back into production. Minimum: a validity window in the projection. Stronger: a spent-ticket record or an issue-time nonce.
2. **Scope fields must be verifiable, not merely disclosed.** A machine verifier must check the ticket authorizes *this* repository, environment, and pipeline. Those live in `executionContext`, which the projection redacts — so the projection must carry the execution-context fields the profile or mandate **declares disclosable** (the default-none principle supplies the mechanism).

The reference verifier (the production website release) already enforces action class, scope binding by independently recomputed content hash, a 1800-second freshness window, and a clock-skew guard. Its two open gaps are exactly the ones above. Related, smaller pieces of the same machine-verification surface, none started: content negotiation on the public ticket URL (JSON for agents), a `.well-known` discovery document, a structured ticket marker in email headers, and a verifier helper plus ticket types in the core library.

### Verifier policy for external relying parties — targets v0.8

v0.6 made verifier policy the **primary enforcement tier** for owner signatures ("the relying party demands a minimum `binding`… MUST fail, not warn") but defined no interface for a relying party who is not running a gateway. An auditor, a counterparty's system, or a pipeline consuming a bearer ticket has a normative verification *procedure* but no defined way to express its policy (minimum binding, required owners, pinned DIDs) or a standard failure semantics. P4 covers the reference gateway's configuration surface only. Same gap class as the projection above, and the two should land together: a small, declarative verifier-policy document that any conformant verifier evaluates identically.

### Subject export of evidence at the AS — undated (custody half promoted)

The Gatekeeper half — custody of the complete signed ticket, mandate, and issuer key — is normative since v0.7. The remaining half: the authenticated subject can export, at any time, the complete signed tickets issued under their mandates and the mandates behind them, in a self-contained format that verifies offline (issuer key included). This converts *Retention*'s operator-facing export duty into a right the evidence's subject can exercise — while an account still exists; it does not reach the already-terminated case, which is why custody is the primary mechanism and export is the recovery path. Deliberately out of scope: custody on an employer-owned device (a returned laptop surrenders the archive with it — a deployment-profile concern, candidate for user-designated escrow), and any subject access *after* termination, which no protocol text can force on a hostile operator.

### Selective disclosure / per-field commitments — undated (activates when a case requires it)

A single hash over a declared subset is all-or-nothing at disclosure time. Proving *"the environment was production"* without revealing the artifact requires a commitment per field plus a hash over those commitments — and that construction MUST NOT be adopted without a per-field random salt: bound values are frequently short and enumerable, and an unsalted per-field hash is recoverable by enumeration. The sub-mandate direction above is the second case that would need it (proving a subset relation without disclosing the parent).

### Resilience to a Compromised Authority Server — remaining items

Owner signatures (v0.6) removed authority fabrication from the compromised-AS surface; the v0.7 enforcement-class table records exactly what remains honest-operator. Remaining:

- **Transparency log — undated.** An append-only, independently auditable log of signed mandates and tickets — equivocation, ignored revocations, and cumulative-cap violations become detectable. To be worth its cost it must be **external or multi-witness**: an AS-run log is no defence against the AS. Its justification is the irreducible residue — cumulative state and pre-flight ordering are claims about a sequence only the AS witnesses, and a witnessed log is the only mechanism on the table that reaches them.
- **Approver public-key authenticity — open; targets `intent-disclosure@0.2`.** The approver keys that wrap the content key are served by the AS unauthenticated and bound into nothing signed — `intent_disclosure_hash` freezes the approver *set*, not their *keys*. Binding the map into the signed payload makes only *later* substitution detectable; what holds is a key the verifier never receives from the AS. These are **encryption** (X25519) keys where `did:key` here carries an Ed25519 **signing** key, so closing this needs either an identifier that carries an X25519 key or a defined derivation — not to be taken casually. The hash-definition change is breaking, hence the companion-spec version bump.

### Output Provenance — profile-bound, undated

Binding a mandate to an observable output location (`output_ref` in the scope schema, hashed and signed) remains specified and unpromoted: it lands in the deploy-style profile that adopts it, not in HAP Core. Maturity marker: no external integrator.

### `eudi` wallet integration — P5, undated

The `binding: "eudi"` value and its validation semantics are normative; what remains is the wallet integration itself and its rotation story — tracked here because it is also the answer to key rotation, which no rotation chain or AS-mediated mechanism can provide.

### The public layer — not a protocol item, recorded once

The vocabulary is now the specification's. The website, the reference implementation's product copy, and the AI-facing context documents still use the v0.6 words. They follow the specification, not the other way round; the change is a copy proposal outside this ledger and is mentioned here only so the sequence is on record: spec first, wire second, copy third.
